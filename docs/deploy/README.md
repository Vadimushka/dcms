# Локальный стенд

## Требования

Docker с плагином compose. На машине могут работать другие проекты —
стек намеренно изолирован: project name `dcms`, порты публикуются только
на `127.0.0.1` и смещены относительно стандартных.

## Запуск

```bash
cp .env.example .env
docker compose up -d --build
```

| Что | Адрес |
|---|---|
| Сайт | http://127.0.0.1:8090 |
| phpMyAdmin | http://127.0.0.1:8091 |
| MySQL | 127.0.0.1:33061 |

Порты меняются через `.env`. Занимать 80, 443, 3306, 5432, 8080 нельзя —
они используются другим окружением на машине.

## Данные

`sys/ini/settings.ini` в репозиторий не входит. Для стенда он берётся
с боевого сервера, в нём правятся параметры подключения:

```bash
ssh vds-vadimushka_d-www-root 'cat ~/www/dcms.vadimushka-d.ru/sys/ini/settings.ini' > sys/ini/settings.ini
sed -i -E "s/^(mysql_host)\s*=.*/\1 = mysql/; s/^(mysql_base)\s*=.*/\1 = dcms/; s/^(mysql_user)\s*=.*/\1 = root/; s/^(mysql_pass)\s*=.*/\1 = dcms/" sys/ini/settings.ini
```

Дамп базы:

```bash
ssh vds-vadimushka_d-root 'mysqldump --single-transaction --default-character-set=utf8mb4 dcms' \
  | docker compose exec -T mysql mysql -uroot -pdcms dcms
```

Боевой сервер используется только на чтение (`mysqldump`, `cat` файла
настроек) — ничего на нём не меняется и не перезапускается.

## Требования к версии PHP

Движок требует PHP 8.1 или новее (проверяется через `composer.json`).
Стенд собирается на версии из `PHP_VERSION` в `.env`, по умолчанию 8.5 —
на ней и ведётся разработка. Совместимость с PHP 5.6 и 7.x больше не
поддерживается: выкатывать ветку можно только после того, как боевой сайт
переключён на 8.1+, отката на старую версию нет.

### Настройки PHP на боевом

Раньше их задавал `.htaccess` через `php_flag`/`php_value`, но с PHP-FPM
эти директивы не действуют — значения нужно выставить в конфигурации PHP
на хостинге (в ISPmanager — настройки версии PHP для сайта):

```ini
; обязательно: движок больше не глушит вывод ошибок сам,
; а переход с 5.6 поднимет много новых предупреждений
display_errors = Off
display_startup_errors = Off
log_errors = On

upload_max_filesize = 100M
post_max_size = 100M
default_charset = UTF-8
arg_separator.output = "&amp;"
; передача сессии в URL: устарела в PHP 8.5, утекает через Referer
session.use_trans_sid = 0
```

Если сайт стоит за обратным прокси с HTTPS, прокси должен передавать
`X-Forwarded-Proto: https` — по нему движок помечает куки признаком
`secure` (см. `is_https()` в `sys/inc/initialization.php`). Заголовок
прокси обязан **перетирать**, а не пропускать клиентский: в nginx это
`proxy_set_header X-Forwarded-Proto $scheme;`. Иначе признак TLS задаёт
посетитель, и при включённой галке «Принудительное использование https»
он же решает, применять ли переадресацию.

### Правила доступа веб-сервера

Под Apache всё нужное уже лежит в `.htaccess` — корневом и 23 вложенных
(`sys/inc`, `sys/ini`, `sys/plugins`, `files/inc`, `forum/inc`,
`install/inc` и других). **Если сайт переводится на nginx, ни один из них
не читается**, и правила нужно перенести в конфигурацию сервера:
`docker/nginx/default.conf` — готовый и проверенный образец, из него
берутся блоки «Deny access», страницы ошибок и роутинг; менять в нём
придётся только `root` и `fastcgi_pass`.

Без этих правил снаружи открыты, в порядке опасности:

| Путь | Что утекает |
|---|---|
| `/sys/ini/settings.ini` | пароль к базе и соль паролей |
| `/sys/inc/`, `/sys/plugins/` | исходники движка |
| `/vendor/`, `/docker/`, `/docs/`, `/tests/` | зависимости, конфигурация, сценарий выката |
| `/sys/files/` | файлы обменника в обход прав доступа |

Ломается без них и работа сайта: пропадает переадресация `/<страница>.php`
→ `pages/<страница>.php` (на неё завязаны все ссылки меню), страницы
ошибок и запрет исполнения PHP в каталоге картинок, куда файл попадает
под именем, заданным загрузившим.

Отдельно на nginx задаётся предел размера тела запроса — `.htaccess` его
не касался, а по умолчанию он много меньше 100 МБ, и выгрузка в обменник
оборвётся ещё до PHP:

```nginx
client_max_body_size 100M;
```

Проверка перед выкатом:

```bash
composer lint       # синтаксис
composer phpstan    # статический анализ
tests/smoke/run.sh  # страницы и сценарии: код ответа, фрагмент, отсутствие PHP-ошибок
```

Набор можно направить и на боевой адрес (`tests/smoke/run.sh https://…`),
но тогда он проверяет только страницы: сценарии входа меняют состояние
сайта и не выполняются, лог PHP недоступен. Об этом он пишет в итоге —
«провалено: 0» после такого прогона означает меньше, чем после местного.

## Обновление структуры БД при выкате

Схема «запомнить меня» переведена с пароля в COOKIE на токены, для них
нужна таблица `users_tokens`. Её структура лежит в
`sys/preinstall/table.users_tokens.structure.json` — на боевом сайте
таблица создаётся штатной страницей админки «Обновление структуры
таблиц» (`/dpanel/dev.update_tables.php`), отметив `users_tokens` и `load`.

До создания таблицы сайт работает: вход по логину и паролю, выход и смена
пароля проходят штатно, не работает только «запомнить меня» — каждый раз
придётся входить заново. В лог PHP при этом пишется строка вида
`user_token: … Table '…users_tokens' doesn't exist (нужна таблица…)`.

Выкат разлогинивает всех, кто был «запомнен»: старые COOKIE содержали
пароль, зашифрованный mcrypt, и новой схемой не читаются. Пользователям
достаточно войти заново.

## Остановка

```bash
docker compose down          # контейнеры
docker compose down -v       # вместе с данными MySQL
```
